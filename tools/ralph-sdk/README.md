# Ralph на Codex SDK

Отдельный пакет, не использует и не изменяет `tools/ralph`.
Нужны Node.js 22+, Git, авторизованный `gh`, доступ к Codex
(`codex login` или `OPENAI_API_KEY`) и окружение проекта для `make check`.
Используется официальный [`@openai/codex-sdk`](https://developers.openai.com/codex/sdk/).

```sh
cd tools/ralph-sdk
npm ci
npm run once -- 18
npm run ralph -- 18 42
npm run phase -- 21 22 23 --dry-run
npm run phase -- 21 22 23
```

`once` выполняет одну попытку и оставляет изменения для ручной проверки.
`ralph` обрабатывает указанные задачи последовательно: попытка → ревью →
доработка → повторное ревью → коммит → комментарий в issue.
Скрипт не пушит, не закрывает задачи и не создаёт PR.

## Попытка

`lib/ralph.ts` экспортирует `ralph(issueNumber, { workingDirectory, onEvent?, extraReviewRounds? })`.
`extraReviewRounds` явно возобновляет сохранённую остановленную попытку,
добавляя указанное положительное целое число к её лимиту ревью.
Возвращает `{ issue, status: "committed" | "stopped", reason?, commit?, rounds, tokens, branch }`.
Git, gh, make check и потоки исполнителя/ревьюера работают в `workingDirectory`.
Callback получает `{ stage, round, tokens, event?, message? }`: этапы
`attempt / check / review / fix / commit` и исходные события SDK.
При наличии callback Ralph ничего не печатает.

`lib/attempt.ts` получает задачу и Codex, возвращает
`{ threadId, checkOk, fixes, report, usage }`. `report` содержит `summary` и `files`.
Оба запуска используют одну реализацию, печать событий вынесена в `lib/log.ts`.

Заголовок и описание загружаются через `gh issue view --json`.
Исполнитель работает в переданном `workingDirectory` (в CLI — корень Git) с `workspace-write`, `approvalPolicy: never`
и моделью из настроек Codex. Поток событий печатает короткие команды,
коды выхода и изменённые файлы; полный stdout сохраняется в логах проверок.
Агенту запрещено запускать `make check`, Ralph, коммитить и менять GitHub.

После хода сам раннер выполняет `make check`. При сбое он передаёт последние
120 строк (до 24000 символов) исполнителю в том же потоке. Разрешены два
исправления, затем незелёная проверка останавливает задачу без коммита.
Та же проверка выполняется после доработки замечаний ревью.

## Ревью и завершение

Каждое ревью получает отдельный `startThread` с `read-only` и reasoning `high`.
Ответ проверяется Zod-схемой `{ findings: [{ priority, file, line, text }] }`,
переданной как `outputSchema` через `zodToJsonSchema(..., { target: "openAi" })`.
Для конвертера используются совместимые схемы `zod/v3` из установленного Zod 4.
Наличие P0/P1 определяет код. Между раундами актуальные P0/P1 целиком
передаются через `resumeThread` исполнителю с прежними опциями. После исправления
раннер выполняет `make check` с теми же двумя попытками исправить сбои;
следующее ревью начинается только после зелёной проверки и получает новый поток.
Максимум задаёт `RALPH_MAX_REVIEW_ROUNDS` (по умолчанию 2, положительное целое).
P2/P3 не блокируют коммит и перечисляются в комментарии.

При одобрении скрипт выполняет `git add -A`, исключая `.ralph`, затем коммит
`<заголовок задачи> (#N)` с `summary` в теле. Новая задача требует чистой
рабочей копии. После остановки правки остаются; следующая новая задача
также остановится, если рабочая копия не чистая.

Комментарий через `gh issue comment --body-file` содержит результат,
файлы, число раундов, открытые замечания с файлами и строками и токены.
При остановке добавляется причина. Итоговая строка каждой задачи:
номер, `commit`/`stopped`, раунды, токены, хеш. Exit 0 — только если все
задачи закоммичены и комментарии опубликованы.
Причина остановки также печатается в stderr после итоговой строки.

## Ограничения и восстановление

| Переменная                | По умолчанию      | Назначение                                                    |
| ------------------------- | ----------------- | ------------------------------------------------------------- |
| `RALPH_REVIEW_MODEL`      | `gpt-6-astra`     | Модель ревьюера                                               |
| `RALPH_WORKER_SANDBOX`    | `workspace-write` | Режим исполнителя: `workspace-write` или `danger-full-access` |
| `RALPH_MAX_REVIEW_ROUNDS` | `2`               | Число раундов ревью новой попытки                             |
| `RALPH_MAX_TOKENS`        | `3000000`         | Сумма input + output всех завершённых ходов задачи            |
| `RALPH_TURN_TIMEOUT_MIN`  | `20`              | Таймаут каждого хода через AbortController                    |

Cached input уже входит в input и повторно не суммируется. SDK сообщает usage
при `turn.completed`; незавершённые ходы не дают точного счётчика расхода.
Лимит проверяется до следующего хода и после каждого полученного usage.
При превышении бюджета или таймауте задача останавливается с комментарием,
обработка очереди продолжается.

Для задач с Docker, локальными серверами и внешней сетью можно явно задать
`RALPH_WORKER_SANDBOX=danger-full-access`. Это даёт исполнителю доступ вне
песочницы с правами запускающего пользователя; используйте режим только для
доверенного проекта. Настройка применяется и при `resumeThread`, а ревьюер
сохраняет `read-only`. Сам процесс Ralph также должен быть запущен вне
ограничивающей песочницы: дочерний процесс не может снять ограничения родителя.

После каждого шага `.ralph/state-N.json` атомарно сохраняет `issue`, `stage`,
`round`, `workerThreadId`, `tokens`, `findings`, а также отчёт и позицию внутри
попытки. При повторном запуске этап продолжается, проверка чистоты пропускается,
существующие потоки восстанавливаются через `resumeThread`. Этап `check`
не повторяет уже завершённый ход. Прерванное ревью восстанавливает свой поток;
следующий раунд создаёт новый. Перед коммитом сохраняется HEAD, чтобы
восстановление после коммита не создало второй коммит.

После успешного коммита и финального комментария состояние удаляется.
У остановленной задачи оно остаётся на этапе `stopped`: сохраняются прежний
поток исполнителя, последние замечания, отчёт, usage, лимиты и этап продолжения.
Изменения остаются в рабочей копии; у фазы сохраняются ветка и worktree.
Обычный перезапуск возвращает результат остановки без новых ходов модели.
Если GitHub недоступен,
состояние остаётся на этапе `comment`: повторный запуск повторяет публикацию,
не работу агента. При аварии между публикацией и удалением состояния возможен
повторный комментарий. `.ralph/` исключена из Git.

Явное продолжение после исчерпания ревью (команды из каталога пакета):

```sh
npm run ralph -- --resume 22 --extra-review-rounds 3
# Для задачи, остановленной в worktree фазы, используйте основную копию:
npm run phase -- 21 22 23 --resume 22 --extra-review-rounds 3
```

Например, после остановки на 2-м ревью добавление 3 даёт общий лимит 5.
Сначала исполнитель исправляет последние P0/P1 в прежнем потоке, затем
раннер выполняет проверки и новое ревью. Повторная реализация с нуля не запускается.
`--resume` и `--extra-review-rounds` обязательны вместе; номер должен входить
в список задач (у `ralph` можно указать только `--resume N`). Отсутствие сохранённой
остановленной попытки — ошибка. Изменение `RALPH_MAX_REVIEW_ROUNDS` само по себе
не увеличивает лимит существующей попытки.

Токены суммируются за всю попытку, включая возобновления. Сохранённые
`RALPH_MAX_TOKENS` и таймаут хода продолжают действовать: новые настройки могут
их уменьшить, но не увеличить. Дополнительные раунды не дают нового бюджета.
При сбое процесса во время продолжения повторите обычную команду без `--resume`:
активное состояние уже содержит дополнительные раунды и автоматически восстановится.
Повторное исчерпание снова требует явного продолжения.

У остановок старых версий без `state-N.json` одного `result-N.json` недостаточно
для продолжения: нужны сохранённый поток, актуальные замечания и полный usage.
Обычный запуск с сохранённым результатом `stopped` также не создаёт новую попытку.
Не восстанавливайте счётчики из результата первого хода: он не включает последующие
исправления и ревью.

Все состояния, отчёты и логи хранятся по абсолютному пути `.ralph/` рядом
с запущенным пакетом в основной копии, независимо от worktree.
Артефакты `once`: `.ralph/artifacts/issue-N-*/thread.json`, `check-*.log`,
`result.json`. У `ralph`: `.ralph/artifacts/issue-N/<этап>-<раунд>/`,
`.ralph/comment-N.md` и `.ralph/result-N.json`. Историю потоков хранит Codex.
`once` всегда создаёт новую попытку; автоматическое восстановление есть у `ralph`.

```sh
npm test
npx tsc --noEmit
```

Эти проверки не обращаются к модели и GitHub. Полный `ralph` запускается
отдельно, поскольку создаёт коммиты и комментарии.

## Оркестратор фазы

`npm run phase -- 21 22 23` строит волны и запускает до `PHASE_PARALLEL` задач
одновременно (по умолчанию 3). `--dry-run` только читает GitHub и журнал,
показывает зависимости и волны; чистая рабочая копия для него не требуется.
Основной запуск требует чистой основной копии на локальной ветке (detached HEAD
не поддерживается). Текущая ветка основной копии становится базой фазы:
переключитесь на нужную ветку перед запуском.

```sh
git switch feature/my-phase
npm run phase -- 21 22 23
```

Парсер понимает `Зависит от: #21, #22` и несколько строк `Зависит от #21 — название`.
Зависимость выполнена, если issue закрыта в GitHub или номер есть в `merged`
журнала `.ralph/phase.json`. Открытая зависимость вне списка блокирует задачу
и её потомков. Цикл останавливает фазу до любых запусков.
Уже закрытые выбранные задачи не запускаются; уже слитые берутся из журнала.

Каждая задача получает ветку `ralph/N` и соседний каталог `../<репозиторий>-wt-N`
от базовой ветки. Существующие ветка и зарегистрированный worktree переиспользуются.
В новой копии устанавливаются npm-зависимости корня (`--ignore-scripts`, чтобы
не менять общие Git-хуки) и web. По текущему Makefile отдельная генерация
для make check не требуется; Go загружает модули при проверке.

Готовые задачи сразу поступают в последовательную очередь: `git rebase <базовая-ветка>`,
`make check` в worktree, `git merge --ff-only` в основной копии, удаление worktree
и ветки, запись в журнал. Следующая волна начинается после завершения предыдущей.
Конфликт прерывается через `git rebase --abort`. При остановке или отказе слияния
ветка и worktree сохраняются, публикуется комментарий с причиной и продолжением;
зависимые пропускаются, независимые продолжают работу. Push, закрытие issue и PR
не выполняются.

`PHASE_MAX_TOKENS` (по умолчанию 9000000) ограничивает сумму input + output задач
фазы, включая usage возобновлённых задач. При достижении лимита новые задачи
не запускаются, уже начатые завершаются. Незавершённый ход SDK не сообщает
точный расход; параллельные начатые задачи могут превысить лимит при завершении.

Таблица в терминале обновляется ANSI-кодами раз в секунду. События пишутся в
`.ralph/logs/N.jsonl`, проверка после rebase — в `N-merge-check.log` рядом.
Итог с причинами, раундами, токенами и временем сохраняется в
`.ralph/phase-report.md`. Exit 0 — только если все выбранные задачи слиты.

После сбоя повторите ту же команду из основной копии на той же базовой ветке.
Журнал `.ralph/phase.json` сохраняет `baseBranch`; запуск на другой ветке
отклоняется, в том числе при `--dry-run`. Старые журналы без этого поля
относятся к `main`. Для независимой фазы на другой ветке сначала архивируйте
весь каталог `.ralph/`, чтобы не переиспользовать прежние состояния и результаты.
Сохранившиеся ветки `ralph/N` и worktree также переиспользуются: завершите
прежнюю работу перед повторным использованием тех же номеров задач. `.ralph/result-N.json`
и `tasks` журнала сохраняют результат Ralph, включая остановку, до слияния: модель повторно
не запускается. Сбой после ff-merge восстанавливается проверкой предка базовой ветки
и завершением очистки. При незелёной проверке слияния исправьте worktree,
закоммитьте исправление вручную и повторите фазу. При остановке самого Ralph
используйте `--resume N --extra-review-rounds K` с полным списком задач фазы.
Уже слитые задачи учитываются из журнала, возобновлённая задача проходит обычное
слияние, затем запускаются разблокированные зависимости. Usage сохранённых
результатов и незавершённых состояний учитывается до запуска новых задач;
исчерпание бюджета фазы не мешает завершить очистку уже выполненного ff-merge.

`node --test` проверяет волны, парсинг зависимостей, последовательность слияний,
блокировку потомков, бюджет, конфликт rebase и восстановление после ff.
Интеграционные тесты используют временные Git-репозитории в `tmp/`,
подменяют gh/npm/make и не обращаются к модели или GitHub.
