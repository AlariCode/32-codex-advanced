# Linkbook

Монорепозиторий приложения для хранения ссылок на статьи и последующего чтения.
Реализованы страница Next.js, HTTP API с регистрацией и входом пользователей и проверкой
состояния, автомиграции PostgreSQL, отдельный процесс Worker и локальный pgvector.

## Стек

- Web: Next.js 16, React 19, TypeScript, App Router, обычный CSS, npm.
- API: Go 1.26, стандартный `net/http`.
- Worker: PostgreSQL-очередь, защищённая загрузка HTTP(S), Readeck и текстовый архив.
- База: PostgreSQL 18, pgvector 0.8.6, Docker Compose.

## Локальный запуск

Нужны Node.js 22+, npm, Go 1.26+ и запущенный Docker с Compose v2.
Все команды ниже выполняются из корня репозитория.

```sh
make setup
make db-up
```

Затем в трёх отдельных терминалах:

```sh
make web
```

```sh
make api
```

```sh
make worker
```

- Web: <http://localhost:3000>.
- API: <http://localhost:8080/healthz>, ответ `{"status":"ok"}`.
- PostgreSQL: `localhost:15432`, база и пользователь `linkbook`.

`make setup` создаёт локальный `.env` из примера и устанавливает зависимости
по lock-файлам в корне и в `web/`, а также устанавливает Git-хуки Lefthook.
Make передаёт настройки `.env` Go-процессам, а Compose читает
его автоматически. Примерные учётные данные предназначены для локальной разработки.
Если изменён `POSTGRES_PORT`, обновите также `DATABASE_URL`,
`WORKER_DATABASE_URL` и `WORKER_DATABASE_PORT`. Для существующего `.env` добавьте
поля worker из `.env.example`. `WORKER_DATABASE_HOST`/`PORT` должны обозначать
тот же контейнерно-доступный PostgreSQL endpoint, что и `WORKER_DATABASE_URL`.

`make worker` запускает `compose.worker.yaml`: firewall блокирует внутренние сети,
разрешая только точный endpoint PostgreSQL и DNS; IPv6 egress в этом окружении
закрыт. После настройки firewall процесс теряет capabilities и работает как UID
65532, с ограничениями 512 MiB RAM, одного CPU, 64 процессов и 256 файлов.
`make worker-dev` запускает Go-процесс без контейнерной сетевой изоляции;
используйте его только для локальной отладки. Проверка deployment-policy:
`sh scripts/check-worker-egress.sh`.

API требует `DATABASE_URL`, подключается к PostgreSQL и применяет миграции перед
запуском HTTP-сервера. Если база недоступна или миграция не проходит, API завершает
запуск с ошибкой. `/healthz` проверяет доступность HTTP-процесса.
Worker подключается к PostgreSQL и до 60 секунд ожидает совместимую схему 001–006
с диагностикой; миграции применяет только API. Генерация embeddings и семантический
поиск пока не реализованы.

`POST /api/users/register` принимает JSON с `email` и `password`, создаёт
пользователя и возвращает `201` с `id`, нормализованным `email` и `created_at`.
Пароль — от 8 любых Unicode-символов, включая пробелы; в базе хранится хеш Argon2id.
Подробный [контракт регистрации](backend/api/registration.md).

`POST /api/users/login` проверяет email и пароль, возвращает `200` с публичными
данными пользователя и защищённую cookie `linkbook_session`. Сессия сохраняется
в БД как хеш случайного токена и истекает через 24 часа. Для cookie нужен HTTPS.
Подробный [контракт входа](backend/api/login.md). Сессия также защищает личную библиотеку и `GET /api/users/me`. Выход пока не реализован.

Страница регистрации: <http://localhost:3000/register>. Форма отправляет запрос
на `/api/users/register` через серверный прокси Next.js, показывает ошибки API
и после успеха сразу открывает личную библиотеку. Регистрация одной транзакцией
создаёт пользователя и сессию. Пароль не обрезается; длина проверяется по Unicode-кодовым точкам.
Форма и её API/валидация остаются в слайсе страницы по FSD v2.1, а общие элементы
интерфейса экспортируются через `shared/ui/index.ts`.

Страница входа: <http://localhost:3000/login>. Форма отправляет запрос на
`/api/users/login` через серверный прокси Next.js. Проверяет заполнение полей
и очевидные ошибки email, сохраняет пароль без изменений, поддерживает
автозаполнение и показ пароля. Неверный email/пароль, ошибки сервера и сети
показываются в форме с возможностью повторить запрос. Во время отправки
поля заблокированы; после успеха пароль очищается, и пользователь сразу
переходит в личную библиотеку. Cookie сессии обрабатывается браузером, токен не хранится в JavaScript.

По умолчанию Next.js обращается к `http://127.0.0.1:8080` (или порту `API_PORT`).
Для другого адреса задайте серверную переменную `API_ORIGIN` в `web/.env.local`
или окружении процесса и перезапустите Next.js. При production-сборке задайте
тот же адрес перед `npm run build`: rewrites сохраняются при сборке.

## Личная библиотека

Главная страница проверяет сессию и показывает владельцу его ссылки, новые сверху.
URL сохраняется вместе с durable-заданием в одной транзакции. Дубликат возвращает
существующую карточку; другой владелец получает отдельную запись. До ответа API
карточка явно показывает отправку, а ошибки позволяют исправить URL или повторить.
Сохранённые карточки переживают reload; 401 скрывает личное содержимое.

Задайте API `PUBLIC_ORIGIN`, совпадающий с origin браузера (по умолчанию
`http://localhost:3000`). Миграции добавляют links, processing_jobs и snapshots,
а общий модуль `backend/linkprocessing` входит в workspace и проверки.
Worker загружает HTML до 3 MiB после декомпрессии и извлекает текст через Readeck.
Библиотека опрашивает processing каждые две секунды, включая карточки вне текущей
страницы; скрытая вкладка приостанавливает частый polling. Готовая карточка
открывает `/links/[id]`; читалка получает сохранённый документ из PostgreSQL
и работает при отключённом оригинале. Сетевые ошибки остаются в карточке.
Блоки кода сохраняют переносы и отступы и показываются с подсветкой синтаксиса.
Читалка поддерживает архивные изображения и форматированные блоки; для
failed/unavailable доступен ручной повтор обработки.
Подробный [контракт библиотеки и покрытие критериев](backend/api/library.md).

При 401 во время сохранения, polling или чтения (включая приватные изображения)
содержимое сбрасывается,
и открывается вход с `returnTo`. После входа разрешён только `/` либо путь
`/links/<id>`; сессия и доступ к статье проверяются заново. Чужая или исчезнувшая
статья показывает сообщение и переход в библиотеку. Focus, online и pageshow
перепроверяют аккаунт и данные; history snapshot скрывает приватное UI до
проверки аккаунта. Уведомление о входе в другой вкладке сбрасывает старое UI.

Ввод и предварительные карточки сохраняются в localStorage под ключом
`linkbook:drafts:v1:<user_id>` и восстанавливаются после проверки владельца.
Там хранятся только локальный ID, публичный user_id, URL, состояние и время,
без токенов или паролей. Прерванная отправка восстанавливается с неизвестным
исходом и требует явного повтора. Повтор использует серверную дедупликацию:
после подтверждения локальный черновик удаляется, существующая карточка получает
фокус. При запрете localStorage есть предупреждение, работа продолжается в памяти.

Ошибки первой загрузки списка и читалки имеют кнопку «Повторить». При сетевом
сбое обновления сохраняются загруженные страницы, документ, ввод и черновики.
Явный повтор снимает ошибку после успешного ответа; повтор загрузки не создаёт
новую задачу обработки. Проверки фазы 3 описаны в
[отчёте](docs/validation/phase-3.md).

## База данных

```sh
make db-shell
```

Проверка расширения и векторной операции в psql:

```sql
SELECT extversion FROM pg_extension WHERE extname = 'vector';
SELECT '[1,2,3]'::vector <-> '[1,2,4]'::vector AS distance;
```

Второй запрос должен вернуть `1`.

Данные сохраняются в named volume. `make db-down` останавливает базу,
сохраняя данные; `make db-logs` показывает логи. Init-скрипты запускаются
только при создании пустой базы. Для уже существующей базы расширение
можно включить вручную: `CREATE EXTENSION IF NOT EXISTS vector;`.

Миграция `backend/migrations/001-create-users.sql` создаёт таблицу пользователей.
История и контрольные суммы миграций хранятся в `schema_migrations`.
Повторный запуск API не применяет SQL повторно; параллельные запуски защищены
блокировкой, ошибки SQL откатываются транзакцией. SQL встроен в бинарник и
не зависит от каталога запуска. Правила добавления миграций описаны в
[backend/migrations/README.md](backend/migrations/README.md).
Таблицы и размерность embeddings пока не задаются.

## Проверки и сборка

```sh
make check
make build
```

`make check` проверяет Go-пакеты, запускает `go vet`, ESLint и TypeScript.
`make build` собирает Go-бинарники в `bin/` и production-сборку Web.
После сборки Web можно запустить командой `npm start`.

### Git-хуки

Lefthook устанавливается при `npm ci` в корне (также входит в `make setup`).
Для повторной установки хуков выполните `npx lefthook install`.

- `pre-commit`: Prettier и `gofmt` форматируют подготовленные к коммиту файлы
  и добавляют исправления в индекс; затем запускаются `npm run lint`
  (ESLint и `go vet`) и `npm run typecheck` (TypeScript).
- `pre-push`: `npm test` запускает все Go-тесты, включая интеграционные,
  во всех трёх модулях, без кеша. Playwright запускается отдельно через `npm run test:e2e`.

Для `pre-push` нужен работающий Docker: команда автоматически поднимает
тестовую PostgreSQL из `compose.test.yaml`. После тестов контейнер остаётся
запущенным для повторных проверок; остановить его можно через `make test-db-down`.
При ошибке любой проверки коммит или push прерывается.
Форматирование вручную: `npm run format -- <путь>` и `gofmt -w <путь.go>`.

## Интеграционные тесты регистрации

### Проверки интерфейса Playwright

```sh
npm ci --prefix web
cd web
npx playwright install chromium
cd ..
npm run test:e2e
```

Тесты находятся в `web/tests/e2e/` и проверяют главную, регистрацию и вход на
мобильном, планшетном и десктопном разрешениях, а также ширины рядом с
адаптивным брейкпоинтом. Проверяются локальная валидация email, исправление
ошибок, клавиатурная навигация, состояние отправки и подтверждение регистрации.
Для входа также проверяются переходы между страницами, пустые поля,
неверные учётные данные, точная передача пароля, ошибки сервера и сети,
некорректные ответы, повторная попытка и защита от двойной отправки.
Ответы API подменяются: эти проверки не создают аккаунты и не требуют базы.
Playwright автоматически запускает отдельный Next.js на `127.0.0.1:3100`.
Перед запуском остановите `npm run dev` для этого проекта: Next.js не допускает
два dev-процесса с одним каталогом `.next`.
Видео всех прогонов сохраняются в `tmp/playwright/videos/`, в подпапке каждого
теста; папка исключена из Git. Следующий запуск заменяет предыдущие артефакты.

### Проверки API и базы

```sh
make test-db-up
make test-integration
make test-db-down
```

Тесты используют отдельный PostgreSQL 18 на порту `15433`, базу `linkbook_test`
и реальные миграции из `backend/migrations`. Для каждого сценария создаётся
отдельная схема, которая удаляется после теста. Данные тестового контейнера
хранятся в памяти; рабочая база на порту `15432` не используется.

`make test-integration` передаёт `TEST_DATABASE_URL` из Makefile; его можно
переопределить для своей тестовой базы с именем `linkbook_test`. Прямой запуск
`go test -tags=integration` требует явно задать эту переменную. Отсутствующая
или недоступная база приводит к ошибке, тесты не пропускаются.

Тесты проверяют регистрацию через HTTP-обработчик, записи в базе и автомиграции:
повторный запуск, конкурентное применение, откат ошибок и целостность истории.
Обычный `make check` запускает тесты без тега `integration`.
Контракт описан в [backend/api/registration.md](backend/api/registration.md).

### TDD-тесты логина

`make test-db-up && make test-login` запускает сценарии
`POST /api/users/login` на отдельной тестовой PostgreSQL. Ожидаемый контракт
и границы покрытия описаны в [backend/api/login.md](backend/api/login.md).
Тесты прошли этап Red и входят в общий `make test-integration`.
Обычный `make check` их не запускает.

## Сквозная проверка архива

```sh
make test-db-up
npm run test:e2e:integration
```

Команда запускает отдельный Next.js на 3200, настоящий API на 18080, worker,
HTTP fixture-server на 39876 и локальный управляющий endpoint на 39877.
Нужны свободные порты и зависимости из `make setup`; PostgreSQL — из
`compose.test.yaml`. `TEST_DATABASE_URL` необязателен, по умолчанию используется
локальная `linkbook_test` на 15433. Другую базу harness не принимает.
Каждый запуск создаёт собственную схему `e2e_*`, применяет реальные миграции
и удаляет схему/процессы при штатном завершении. При SIGKILL схема может остаться;
её точное имя можно найти в тестовой БД и удалить через harness-команду
`TEST_DATABASE_URL=... tmp/integration/integration-db drop e2e_<имя>`.

Тестовое разрешение действует только для одного точного loopback HTTP origin
в отдельном `cmd/integration-worker`. Production-бинарник не читает
`FIXTURE_ORIGIN` и не содержит настройки отключения policy. Production-защита
дополнительно проверяется Go-тестами с реальными UDP DNS и HTTP/TLS sockets,
включёнными в `make test`. Fixtures проекта не зависят от публичных сайтов.

Mock-прогон `npm run test:e2e` запускается отдельно. Прогоны Next.js одного
checkout следует запускать последовательно: оба набора собирают общий `.next`
и проверяют production Next.js через `next start` с собственным API_ORIGIN.
Видео обоих наборов сохраняются в `tmp/playwright/videos/`, включая успешные
сценарии и второй браузер владельца. [Покрытие #2 и #3](docs/verification/issue-2-3.md).

В набор #4 входят настоящие ожидания 30/120 секунд, 35-секундный Retry-After,
SIGKILL/перезапуск worker и истечение сессии в БД. Длительные процессные сценарии
выполняются один раз проектом `recovery` (1440×900); регрессия архива и mock-проверка
серверного возраста/offline выполняются на трёх разрешениях. Поэтому полный
сквозной прогон занимает около семи минут. Управляющий fixture endpoint остаётся
локальным тестовым инструментом; production worker не получает эти настройки.
[Покрытие #4](docs/verification/issue-4.md).

## Живой benchmark архива

Из корня репозитория, отдельно от детерминированных тестов:

```sh
npm run benchmark:archive -- --output tmp/archive-benchmark-new
npm run benchmark:recalculate -- tmp/archive-benchmark-new/runs.jsonl
```

Команда выполняет 60 последовательных новых сохранений фиксированного RU/EN
корпуса через production API/worker и реальную карточку UI. Она сохраняет
каждую попытку, условия, ошибки и полный отчёт; Exit 0 не означает достижения
порога 54/60. Нужны Docker, Chromium и публичный интернет; используется только
изолированная схема локальной `linkbook_test`.
[Методика и ограничения](docs/verification/issue-12-method.md),
[отчёт приёмки #12](docs/verification/issue-12.md).
