# Контракт входа пользователя

API реализован по TDD-контракту; сценарии находятся в `login_integration_test.go`.

`POST /api/users/login`, `Content-Type: application/json` (допустим `charset=utf-8`).

```json
{"email":"reader@example.com","password":"password123"}
```

Успех: `200`, `Content-Type: application/json`, `Cache-Control: no-store`.
JSON содержит только публичные поля уже существующего пользователя:

```json
{"id":"UUID","email":"reader@example.com","created_at":"RFC3339 timestamp"}
```

Вход не создаёт пользователя и не меняет его данные или хеш пароля.
Email нормализуется как при регистрации: пробелы по краям удаляются,
регистр понижается. Адреса с `+tag` и разным расположением точек различаются.
Пароль проверяется точно, включая регистр, пробелы и Unicode, без нормализации.
Минимум 8 символов относится к регистрации: непустой короткий пароль при входе
возвращает `401`, а не ошибку политики создания пароля.

Выбранная для TDD схема сессий — cookie `linkbook_session` со свежим непрозрачным
токеном при каждом успешном входе. Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`,
`Path=/`, без `Domain`, `Expires` и `Max-Age` (браузерная сессия).
Cookie всегда использует `Secure`; для использования сессии клиентом нужен HTTPS.
Пароль, хеш и токен не возвращаются в JSON. Предоставленная клиентом cookie
не используется как новый токен. Одновременные входы получают разные токены.
Неуспешный вход не выставляет и не заменяет cookie.

Сессии сохраняются в `user_sessions` (миграция `002-create-user-sessions.sql`).
Токен содержит 32 криптографически случайных байта в base64url; в базе хранится
только его SHA-256-хеш, пользователь и даты создания/истечения. Серверный срок
сессии — 24 часа. Если запись сессии не удалась, возвращается `500` без cookie.
Проверка сессий на защищённых маршрутах и удаление истёкших записей пока не реализованы.

| HTTP | code | Сценарий |
| --- | --- | --- |
| 400 | invalid_request | Сломанный JSON, не объект, неверные типы, неизвестные поля, второй объект, лишние данные |
| 400 | invalid_email | Отсутствующий, null, пустой или некорректный email |
| 400 | invalid_password | Отсутствующий, null или пустой пароль |
| 401 | invalid_credentials | Неизвестный email или любой неверный непустой пароль |
| 413 | request_too_large | Тело больше 1 MiB; ровно 1 MiB допускается |
| 415 | unsupported_media_type | Отсутствующий, сломанный или неподдерживаемый Content-Type |
| 500 | internal_error | Недоступная БД или повреждённый/небезопасный формат хеша |

Для ошибок POST также обязателен `Cache-Control: no-store`. JSON ошибки содержит
`code` и необязательное `message`, без внутренних деталей. Ответы `401` полностью
одинаковы для неизвестного email и неверного пароля, чтобы не раскрывать наличие
аккаунта. Тесты не измеряют время ответа и не доказывают защиту от timing attacks.
Другие HTTP-методы возвращают `405`, `Allow: POST` и не выставляют cookie.

## Покрытие и запуск

Тесты проверяют HTTP-обработчик с настоящими миграциями и PostgreSQL. Используется
существующая фикстура регистрации: отдельная схема на каждый тест с очисткой
после завершения, только база `linkbook_test`. Пользователи создаются через API
регистрации, поэтому проверяется совместимость входа с её Argon2id-хешами.

```sh
make test-db-up
make test-login
```

До реализации тесты падали из-за отсутствующего `/api/users/login` (Red).
После реализации маршрута, проверки хеша и выдачи сессии они проходят (Green).
Для проверки регрессий выполните `make test-integration` и `make check`.
Чтобы остановить тестовую БД, выполните `make test-db-down`.

Этот набор покрывает API входа. Проверка использования и истечения сессии,
выход, ограничение попыток входа, CSRF и UI требуют отдельных контрактов
и тестов после определения соответствующих маршрутов и политики безопасности.
