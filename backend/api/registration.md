# Контракт регистрации

`POST /api/users/register`, `Content-Type: application/json`.

```json
{"email":"reader@example.com","password":"password123"}
```

Успешный ответ: `201`, `Content-Type: application/json`.

```json
{"id":"UUID","email":"reader@example.com","created_at":"RFC3339 timestamp"}
```

Пользователь сохраняется в PostgreSQL: `id`, `email`, `password_hash`, `created_at`.
Пароль и хеш не возвращаются клиенту. Хеш — Argon2id в формате PHC с независимой
случайной солью для каждого пользователя. Тесты проверяют исходный и неверный
пароли независимо от приложения.

Email очищается от пробельных символов по краям и приводится к нижнему регистру.
В этом контракте используется обычный адрес без display name и списков адресов.
Локальная часть — максимум 64 байта, метка домена — максимум 63 байта,
адрес целиком — максимум 254 байта. DNS и доставка письма не проверяются.
Адреса с точками и `+tag` не объединяются по правилам отдельных провайдеров.
Нормализованный email уникален, включая одновременные запросы.

Пароль: минимум 8 Unicode-символов (кодовых точек), любых, включая пробелы.
Пароль не обрезается, не приводится к другому регистру и не нормализуется.
Отдельного максимума длины пароля нет; общий предел тела запроса — 1 MiB.

Ошибка возвращается как JSON с непустым полем `code`; поле `message` допустимо.

| HTTP | code | Причина |
| --- | --- | --- |
| 400 | invalid_request | Некорректный JSON, неверные типы, неизвестные поля, лишние данные после объекта |
| 400 | invalid_email | Отсутствующий, пустой или некорректный email |
| 400 | invalid_password | Отсутствующий пароль или менее 8 символов |
| 409 | email_exists | Повтор нормализованного email |
| 413 | request_too_large | Тело больше 1 MiB |
| 415 | unsupported_media_type | Отсутствующий или неподдерживаемый Content-Type |
| 500 | internal_error | Ошибка базы данных без раскрытия внутренних деталей |

Отказ регистрации не создаёт нового пользователя и не изменяет существующего.
Два одновременных запроса с одним email дают один `201` и один `409`.

Тесты используют HTTP-обработчик приложения без моков базы. Каждый сценарий
применяет SQL-миграции в отдельной случайной схеме базы `linkbook_test`.
Инициализация базы в тестах использует тот же код автомиграций, что и запуск API.
Все сценарии регистрации проходят на настоящем PostgreSQL.
