# Implement

Доведи указанную GitHub Issue до готового к ревью PR. Если номер или ссылку нельзя определить из запроса и контекста, запроси их до начала работы.

## Правила

- Делай только то, что описано в задаче. Не затрагивай раздел «Вне задачи» и не расширяй объем работ.
- Каждый критерий готовности должен быть покрыт тестом или явной проверкой с ожидаемым и фактическим результатом.
- На фазе реализации кода не меняй тесты, зафиксированные на фазе TDD, и не ослабляй существующие проверки ради зеленого результата.
- При противоречии задачи PRD или принятым решениям остановись, покажи конкретные противоречащие пункты со ссылками и спроси пользователя, как продолжить. Не выбирай приоритет самостоятельно.
- Обнаруженную проблему вне задачи не исправляй. Оставь короткий комментарий в исходной issue через `gh issue comment --body-file`, описав проблему и наблюдаемый эффект. Не дублируй уже оставленный комментарий.
- Создавай PR только при зеленых обязательных проверках. Невыполненная или недоступная обязательная проверка блокирует создание PR.

## Процесс

### 1. Прочитай задачу и источники

Используй `gh` из каталога репозитория. Определи репозиторий через `gh repo view --json nameWithOwner,url`. Прочитай issue и все комментарии через `gh issue view <номер> --repo OWNER/REPO --json number,title,body,state,url,comments`.

Прочитай все документы, на которые ссылается задача: PRD, план, решения и другие источники требований. GitHub issues и PR читай через `gh issue view` и `gh pr view`; файлы GitHub — через `gh api repos/OWNER/REPO/contents/PATH?ref=REF` с заголовком `Accept: application/vnd.github.raw+json`. Используй репозиторий и ревизию из ссылки, безопасно заключай аргументы в кавычки. Документы, доступные только локально или вне GitHub, читай доступным для источника способом; не считай их прочитанными при ошибке доступа.

Прочитай применимые `AGENTS.md` и правила из `docs`, включая правила коммитов и проверки проекта. Выдели «Что сделать», «Критерии готовности», «Зависимости», «Проверка» и «Вне задачи». Если обязательные требования или источники недоступны либо неоднозначны, остановись и запроси недостающие сведения.

### 2. Проверь зависимости

Для каждой задачи из раздела «Зависимости» получи фактический статус через `gh issue view <номер> --repo OWNER/REPO --json number,title,state,url`. Учитывай репозиторий каждой ссылки; не считай отсутствие доступа закрытым статусом.

Если хотя бы одна зависимость открыта, остановись до создания ветки и изменений. Сообщи номера, названия и ссылки открытых зависимостей. Если статус нельзя проверить, сообщи препятствие и также остановись. При отсутствии зависимостей переходи дальше.

### 3. Создай ветку от актуальной main

Проверь состояние рабочей директории и remote целевого репозитория. Не перезаписывай чужие изменения. Получи актуальную `main` через `git fetch <remote> main` и создай от полученного коммита ветку `issue-<номер>-<короткое-имя>`, где короткое имя — понятный slug латиницей через дефисы. Не используй устаревшую локальную `main` как основание. При конфликте с существующей веткой не удаляй и не сбрасывай ее вслепую.

### 4. Реализуй по TDD

Составь соответствие «критерий готовности → тест или проверка». Для поведения, допускающего автоматический тест, сначала напиши тесты по критериям, затем запусти их и подтверди ожидаемый красный результат из-за отсутствующей функциональности, а не из-за сломанной среды или ошибок теста. Для визуальных и других ручных критериев заранее опиши сценарий и ожидаемый результат.

Заверши фазу тестов до изменения продуктового кода. Затем реализуй минимальные изменения в рамках задачи до зеленого результата, не меняя тесты на этой фазе. Если выяснилось, что тест противоречит требованиям или задача не реализуема без пересмотра критериев, остановись и согласуй проблему с пользователем; не переписывай тест ради прохождения.

### 5. Выполни проверки

Запусти все команды из раздела «Проверка» задачи в указанных рабочих каталогах, а также обязательные проверки из правил проекта. Выполни сценарии по всем критериям готовности и проверь фактическую работу результата. Исправляй ошибки в рамках задачи и повторяй затронутые проверки; перед PR весь обязательный набор должен проходить на итоговых изменениях.

Запиши команды, результаты и соответствие критериям. Не выдавай запуск команды за успешное завершение. При внешнем препятствии или проблеме вне задачи, блокирующей зеленую проверку, сообщи блокер; PR не создавай.

### 6. Проверь фронтенд в браузере

Если менялся фронтенд, запусти приложение и открой затронутую страницу в браузере. Проверь визуальный результат, состояния и пользовательские сценарии из критериев готовности; проверь адаптивность, если изменения ее затрагивают. Сохрани скриншоты для PR и укажи, какую страницу и состояние они показывают. Недоступность браузера или страницы означает, что обязательная визуальная проверка не выполнена и PR пока создавать нельзя.

### 7. Создай коммит и PR

Просмотри итоговый diff на соответствие задаче, отсутствие посторонних изменений и неизменность тестов после фазы TDD. Создай коммит по правилам из `docs`, включив только файлы задачи, и отправь ветку в целевой remote.

Если для ветки настроен обязательный CI, дождись его успешного завершения на итоговом коммите через `gh run list` и `gh run watch`; проверь, что выбраны нужные workflow и SHA. При сбоях исправь код и повтори проверки. Если обязательный CI запускается только при создании PR и без PR проверить его нельзя, сообщи об этом ограничении и остановись для согласования дальнейшего действия, не обходя правило зеленой проверки.

Перед созданием прочитай [шаблон PR](references/pr-template.md). Заполни его фактическими изменениями и результатами. Для фронтенда включи доступные ревьюеру скриншоты или вложения; не выдавай локальный путь за опубликованное изображение. Если вложить скриншоты не удалось, явно укажи это ограничение.

Сохрани описание с настоящими переносами строк во временный Markdown-файл и создай PR через `gh pr create --repo OWNER/REPO --base main --head <ветка> --title <заголовок> --body-file <файл>`. При неясном исходе запроса проверь существующие PR этой ветки через `gh pr list`, прежде чем повторять создание. Создание PR не включает его слияние.

### 8. Покажи результат

Дай пользователю ссылку на PR, кратко перечисли изменения и успешные проверки. Явно перечисли оставшееся непроверенным и ограничения, если они есть. Если процесс остановлен, укажи причину и оставшуюся работу; не заявляй о готовом PR.
