# Feature with Review

Действуй как дирижёр: сам код не пиши. Запускай субагентов, передавай результаты и выполняй общие проверки из корня проекта. Используй существующие роли `scout` и `reviewer` из `.codex/agents/`; новые роли не создавай. Не коммить. Сохраняй id всех субагентов; при любом завершении, включая остановку, закрывай их через `close_agent`.

### 0. Подготовь задачу

Проверь `git status --short --untracked-files=all`. Если есть изменения или неотслеживаемые файлы, остановись и спроси пользователя, как поступить; ничего не очищай и не прячь в stash.

Прочитай `README.md` и применимые `AGENTS.md`. Сформулируй задачу и критерии готовности в одной-двух фразах. Зафиксируй точный список разрешённых для изменения файлов, включая нужные тесты и документацию. Если файлы неясны, сначала запусти ровно одного `scout` с задачей «Какие файлы нужно менять для этой задачи и её проверок?». Запрети ему изменения; используй ответ для списка файлов.

### 1. Запусти исполнителя

Создай одного `worker` без истории сессии. Передай задачу, критерии готовности, применимые инструкции и список файлов. Потребуй:

- Меняй только перечисленные файлы; если нужен другой файл, сообщи дирижёру и дождись уточнения списка.
- Работай по TDD: сначала тест и ожидаемое падение, затем минимальная реализация и зелёный результат. Запускай точечные тесты.
- `make test`, генерацию и миграции не запускай, не коммить.
- В конце перечисли изменённые файлы и результаты точечных проверок.

Запомни id исполнителя. Все доработки поручай только ему через `send_input`; нового исполнителя не создавай. Изменение разрешённого списка передавай ему явно.

### 2. Проверь изменения

Дождись исполнителя, сопоставь изменённые файлы с разрешённым списком и сам запусти `make check`. При красном результате передай вывод тому же исполнителю через `send_input`, дождись исправлений и повтори `make check`. Это не раунд ревью. При блокере окружения остановись и сообщи, что не проверено.

### 3. Запусти ревью

После зелёного `make check` запусти роль `reviewer`. Передай задачу, критерии готовности и указание: «Изменения — в git diff рабочей копии; проверь также новые файлы. Код не меняй. Для каждого замечания укажи приоритет P0–P3, файл, место и причину». Считай каждый завершённый проход ревью одним раундом.

### 4. Обработай замечания

Передай только P0–P1 тому же исполнителю через `send_input`. P2–P3 ему не отдавай; сохрани их для сводки. После исправлений повтори шаги 2 и 3. Выполни не больше двух раундов ревью. Если после второго остались P0–P1, остановись и покажи их человеку. Если P0–P1 нет, переходи к финальным проверкам.

### 5. Заверши проверки

Сам запусти `make test`. При красном результате один раз передай вывод тому же исполнителю через `send_input`. После его исправлений сам повтори `make check` и `make test`. При повторном падении или недоступности проверки остановись и покажи проблему; больше исправлений не запрашивай. Не объявляй итоговые исправления проверенными ревьюером, если они сделаны после последнего ревью.

Закрой всех созданных субагентов через `close_agent`. Не коммить.

### 6. Покажи сводку

Укажи, что сделано и какие файлы изменены; число раундов ревью и исправленные замечания; открытые P2–P3; итог `make check` и `make test`. При остановке добавь причину, оставшиеся P0–P1 и невыполненные проверки. Не выдавай незапущенную или недоступную проверку за успешную.
