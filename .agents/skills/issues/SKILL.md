# Issues

Преврати одну фазу плана в GitHub issues. На этом запуске не реализуй задачи и не нарезай следующие фазы.

## Правила нарезки

- Каждая задача — вертикальный срез с самостоятельно проверяемым результатом через все необходимые слои. Не разделяй работу на «вся БД», «весь API», «весь фронтенд».
- Размер задачи — одна сессия агента и один PR, который можно прочитать за несколько минут. Если задача слишком большая, сужай сценарий, сохраняя проверяемый результат.
- В разделе «Что сделать» описывай ожидаемое поведение или результат, а не последовательность реализации.
- Покрывай выбранную фазу без расширения ее границ. Учитывай уже заведенные задачи; не создавай дубликаты.

## Процесс

### 1. Выбери фазу и прочитай источники

Прочитай план по пути пользователя и связанную PRD. Если путь отсутствует и его нельзя однозначно определить из разговора, запроси его. Используй указанную пользователем фазу; иначе возьми первую явно незавершенную фазу по порядку плана. Если статус фаз неясен, уточни выбор у пользователя. Назови выбранную фазу.

Изучи относящиеся к фазе решения, точки интеграции и существующие команды проверки проекта, чтобы определить реальные границы задач и проверяемые критерии. Не меняй план или PRD.

### 2. Проверь открытые задачи

Используй `gh` из каталога репозитория. Определи целевой репозиторий через `gh repo view --json nameWithOwner,url`. Прочитай заголовки и тела всех открытых issues, включая все страницы. Например, подставив установленный `OWNER/REPO`:

```sh
gh api --paginate 'repos/OWNER/REPO/issues?state=open&per_page=100' --jq '.[] | select(.pull_request == null) | {number, title, body, html_url}'
```

Сопоставляй задачи по результату и границам, а не только по заголовку. Полные дубликаты используй как существующие задачи; при частичном пересечении предложи только недостающий результат. Отметь такие совпадения в черновике. Если `gh` недоступен, нет авторизации или чтение не удалось, сообщи препятствие; не утверждай, что дубликатов нет, и не переходи к созданию.

### 3. Согласуй черновик

Прочитай [шаблон задачи](references/issue-template.md). Покажи компактный список: одна строка на задачу в формате `A — Заголовок — ожидаемый результат — зависит от: B / #123 / нет`. Буквы — временные идентификаторы новых задач, номера — существующие issues. Расположи список в порядке зависимостей; устрани циклы до согласования.

Отдельно покажи существующие задачи, которые уже покрывают часть фазы. Попроси подтвердить список или предложить правки и дождись явного ответа. **Не создавай issues до подтверждения актуального черновика.** При правках обнови список и согласуй измененную версию. Не запрашивай повторное подтверждение уже утвержденного списка, если его объем не изменился.

### 4. Создай issues

После подтверждения заполни все разделы шаблона для каждой новой задачи. Ссылки на PRD и план должны открываться из GitHub; для файлов репозитория используй URL файлов в целевом репозитории. Если источник доступен только локально, явно отметь это и укажи его путь, не выдумывай URL. Укажи номер и название фазы.

Команды проверки бери из проекта и плана, указывай рабочий каталог и сценарий с ожидаемым результатом. Если нужной автоматической проверки еще нет, явно обозначь ее создание в задаче и опиши, как ее запускать; не выдавай предполагаемую команду за существующую. Не заявляй, что проверки будущей реализации уже выполнены.

Создавай задачи последовательно в порядке зависимостей через `gh issue create --repo OWNER/REPO --title 'Заголовок' --body-file /путь/к/временному-файлу.md`. Записывай Markdown с настоящими переносами строк во временный файл, безопасно передавай заголовок и путь в команду. Сохраняй номер и URL каждой созданной задачи; подставляй фактические номера вместо временных идентификаторов в зависимые задачи. В разделе «Зависимости» пиши `Зависит от #123 — название` для каждой зависимости либо `нет`.

Перед созданием повторно проверь открытые issues на появившиеся дубликаты. Совпавшие задачи переиспользуй и сообщи об этом; если совпадение существенно меняет согласованный результат или зависимости, согласуй обновленный список до создания затронутых задач.

При ошибке создания останови дальнейшие записи и покажи уже созданные задачи и остаток. Если исход запроса неясен, сначала проверь через `gh`, появилась ли задача; не повторяй создание вслепую. Не редактируй существующие issues без отдельного поручения.

### 5. Покажи итог

Выведи для каждой созданной задачи номер, заголовок и ссылку. Отдельно укажи переиспользованные issues и задачи, которые создать не удалось, если такие есть. Заверши работу на выбранной фазе.
