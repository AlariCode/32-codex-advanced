# Feature Plan

Подготовь план реализации фичи, опираясь на существующий проект. Работа состоит из исследования, согласования каркаса и подробного плана. Реализацию не начинай.

## Исследование

1. Прочитай PRD по пути, переданному пользователем, и связанные с ним документы. Найди и прочитай все относящиеся к фиче решения в Decisions — в разделе PRD, отдельном каталоге или связанных документах проекта.
2. Изучи инструкции проекта и код в точках интеграции фичи: существующий пользовательский путь, модули, модели данных, контракты, API и проверки. Проследи путь через все необходимые слои. Не предлагай архитектуру по одному PRD без проверки кода.
3. Используй ответы из PRD, Decisions и кода; не спрашивай то, что уже определено. Уточняй только существенные пробелы, которые нельзя разрешить из источников. Неблокирующие допущения обозначай явно.
4. Считай принятые Decisions ограничениями плана. Не пересматривай и не редактируй их по собственной инициативе. Если обнаружен конфликт между решениями, PRD или текущим кодом, покажи конкретные источники, последствия и варианты разрешения; согласуй с пользователем спорную часть до утверждения каркаса. Отличай конфликт от обычного изменения кода, необходимого для реализации принятого решения.

Ссылайся на конкретные документы, решения и места в коде, чтобы пользователь мог проверить основания плана. Не выдавай предположения за установленное поведение.

## Каркас для согласования

Сначала покажи компактный каркас объемом примерно в одну страницу:

- Цель и границы фичи.
- Архитектура: точки интеграции, затрагиваемые модули и путь данных через необходимые слои.
- Список фаз: **одна строка на фазу**, включающая ее название и то, какой сквозной сценарий работает после нее.
- Существенные допущения, риски и нерешенные конфликты, если они есть.

Попроси утвердить каркас или предложить правки. **Не раскрывай подробный план по шаблону до явного согласования пользователем.** При правках обнови каркас и согласуй измененную версию. Если актуальный каркас уже явно утвержден в текущем разговоре, повторное согласование не требуется.

## Правила фаз

- Каждая фаза — работающий вертикальный срез через все нужные для ее сценария слои. Не выделяй самостоятельные фазы «сделать БД», «сделать backend» или «сделать UI» без работающего сквозного результата.
- Первая фаза — самый тонкий полезный срез, проходящий весь путь от входного действия до наблюдаемого результата. Ограничивай охват сценария, сохраняя реальную интеграцию. Заглушки вместо ключевых звеньев не считаются завершенным сквозным путем.
- Следующие фазы расширяют уже работающий сценарий. Количество фаз определяется фичей, а не фиксированным числом.
- У каждой фазы явно укажи проверяемый результат, команды проверки и сценарии для ручного прохождения или браузера с ожидаемыми результатами. Бери команды из проекта; если готовой команды нет, обозначь необходимую новую проверку, не выдумывая существующий скрипт. Эти команды предназначены для будущей реализации, не заявляй, что они уже пройдены.
- В каждой фазе перечисли, что остается на потом, и укажи последующую фазу либо отметку «вне текущего объема». Обязательные требования PRD должны быть покрыты фазами; не прячь их в неопределенное «потом».

## Подробный план после согласования

После согласования каркаса прочитай [шаблон плана](reference/template.md) и заполни все его разделы в указанном порядке. Раскрой утвержденный каркас без новых несогласованных архитектурных решений. Если детализация выявила существенный конфликт или требует изменить архитектуру либо границы фаз, согласуй изменение перед продолжением зависимой части.

## Границы результата

План не содержит кода реализации, псевдокода, SQL-миграций или готовых патчей. Модели и изменения данных описываются декларативно; команды проверки допустимы. Не изменяй код проекта или Decisions и не начинай реализацию после согласования плана. Если пользователь указал путь для плана, сохрани утвержденный подробный документ туда; иначе следуй принятому в проекте месту для планов, а при отсутствии соглашения выдай документ в ответе.
