# Безопасный рефакторинг Linkbook

## Границы

- Сохранять наблюдаемое поведение, HTTP-контракты, UX и данные. Исправления поведения и новые возможности не смешивать с рефакторингом.
- Тесты не трогать: не добавлять, не редактировать, не переносить и не удалять тесты, фикстуры и тестовые помощники. Не менять конфигурацию, assertions, mocks, таймауты, состав запуска или добавлять skip ради зелёного результата.
- Прямой запрет пользователя на изменение тестов имеет приоритет над требованием AGENTS.md обновлять Playwright-тесты. Остальные применимые проверки AGENTS.md сохраняются.
- При запросе только скилла или плана не начинать реализацию рефакторинга.

## Процесс

1. Прочитать AGENTS.md, посмотреть git status, изучить реализацию, контракты и существующее покрытие. Зафиксировать чужие изменения и исходное состояние тестовых файлов; не перезаписывать их.
2. Создать или обновить план в `docs/refactoring/`. Для каждого небольшого самостоятельного шага записать проблему, затрагиваемые файлы, изменение, сохраняемые инварианты и критерий приёмки. Использовать чекбоксы и журнал проверок. План логина и регистрации: [auth.md](../../../docs/refactoring/auth.md).
3. **До изменения кода** выполнить полный набор проверок ниже. Если тесты красные, рефакторинг не начинать: определить причину и восстановить зелёное состояние, сохраняя тесты и контракт. Если это требует изменения поведения, вынести в отдельную задачу. Недоступные проверки считать непроверенными; не отмечать baseline зелёным.
4. Выполнять ровно один шаг плана. Перед ним сохранить обратимую точку восстановления затрагиваемого кода, учитывая незакоммиченные изменения пользователя. Не использовать общий `git reset --hard` или очистку рабочей директории.
5. После шага снова выполнить **весь набор** проверок. Точечные тесты можно запускать для диагностики, но они не заменяют полный прогон. Для frontend также выполнить визуальную проверку и UX-ревью из AGENTS.md, не меняя тесты.
6. Если всё зелёное и контракт сохранён, отметить шаг выполненным и записать команды и результаты. Если нет — оставить шаг незавершённым, локально откатить только свои изменения текущего шага, проверить возврат к зелёному состоянию, скорректировать реализацию и повторить. При сбое окружения устранить его и повторить проверки; не маскировать его изменением тестов. Не переходить к следующему шагу до зелёного результата.
7. Проверить финальный diff: тесты, их конфигурация и чужие изменения не затронуты. В итогах указать выполненные шаги, результаты и оставшиеся ограничения. Зелёные тесты дополнять сравнением контрактов: они не доказывают сохранение непокрытого поведения.

## Полный набор проверок

Из корня репозитория:

```sh
make test-db-up
make check
make test-integration
npm run test:e2e
```

`make check` включает обычные Go-тесты всех трёх модулей, go vet, ESLint и TypeScript. Он **не включает** интеграционные тесты и Playwright. `make test-integration` включает регистрацию, логин и миграции; отдельный `make test-login` не заменяет его.

Использовать только выделенную базу `linkbook_test` из `compose.test.yaml` (по умолчанию порт 15433), не рабочую базу. Playwright сам запускает Next.js на 3100; не запускать второй dev-процесс с тем же `.next`. Видео остаются в игнорируемой `tmp/playwright/videos/`. Не останавливать контейнеры или процессы, которые были запущены пользователем до задачи.

Перед изменениями frontend применять проектный `feature-sliced-design` и читать актуальные локальные инструкции Next.js. Формы и правила отдельных сценариев оставлять в слайсах страниц; выносить только подтверждённо общую ответственность, соблюдая публичные API и направление импортов.
