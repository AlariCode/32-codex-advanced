# Issue 22: повторное использование проверенного media-соединения

2026-11-10. Измеренный источник расходов — повторное создание TCP/TLS-соединений
при последовательной загрузке изображений одной статьи. Исправление выполнено;
новая полная серия дала **57/60 за ≤15 секунд**, при требуемых 54/60.
Повторная интеграционная регрессия **зелёная**: четыре recovery-падения
диагностированы и исправлены в тестах/harness, полный повтор 103/103 прошёл.
`make check` остаётся за внешним раннером. Это не окончательная приёмка всей фичи.

## Диагноз и причинная проверка

Сначала на неизменённом pipeline выполнена новая baseline-серия из 60 сохранений:
**50/60**. Исторические 49/60 из #12 не использованы вместо нового baseline.
События C сопоставлены с `cardId` каждой попытки. У Avito медиана media составляет
14,714 с из 15,632 с работы worker (около 94%); HTML — 0,541 с,
extraction — 0,018 с, publication — 0,320 с. Доминирует media, а не очередь,
парсер или SQL. Полные события и распределения: [baseline](issue-22/baseline/stages.json).

Дополнительный `httptrace`-профиль использует одни и те же сохранённые HTML всех
шести источников, настоящие production safehttp-запросы и тот же archiveImages.
Это отдельная диагностика media без БД/UI; она не подменяет benchmark готовности.
Порядок переключений: before → after → before-control → after-repeat.
Обёртка fetcher позволяет отключить только reuse, сохраняя остальные изменения.

0,202 / 0,240 / 7,518 с из 8,113 с. Сокращается также передача по уже

У всех шести документов SHA-256 одинаков во всех четырёх профилях, число assets

Дополнительно контролируемый локальный benchmark с задержкой 20 мс на новое
соединение и 25 GET даёт 539,4 мс без reuse против 24,2 мс с reuse.
[Результат](issue-22/connection-benchmark.json). Проверки количества соединений
не используют хрупких временных порогов. Переключение причины обратно возвращает
расходы; вывод основан не только на корреляции количества изображений и времени.

## Ограниченное изменение

`archiveImages` создаёт media-сессию только на один проход одной статьи и
закрывает её через defer, включая отмену. Сессия держит не более одного transport
и одного idle-соединения. Повторное использование разрешено только для точного
scheme + host:port + заново проверенного IP. Смена любого компонента закрывает
старый transport. Перед **каждым** запросом и redirect проверяются URL и все
DNS-ответы; private/mixed DNS отвергается даже при существующем соединении.
HTTP/2/coalescing отключён; proxy, cookies и отключение TLS verification
не добавлены. HTML продолжает использовать свежие transports.

Нет общего кеша между пользователями, кеша ответов или DNS. Даже повторная
image-позиция повторно скачивается и расходует бюджет. Порядок кандидатов,
5/20 MiB, 50 изображений, лимит попыток, 25-секундный HTTP-timeout,
общие 120 секунд, heartbeat, отмена и атомарная SQL-публикация не менялись.
Новая проверка подтверждает списание 20 MiB четырьмя повторными/повреждёнными
загрузками, а не только размер уникальных сохранённых assets.

исключительно коду: причинность дополнительно проверена переключением reuse
и локальным опытом. Регрессионные тесты не выполнялись параллельно live-сериям.

настоящие приватные HTTP 200/тип/bytes проверены самой live-серией.

Сохранившиеся ограничения (также присутствуют в baseline):

- MDN теряет короткий вводный абзац над первым разделом; `text_incomplete`
  остаётся. Основные разделы до конца, таблица и код сохранены.
- Cloudflare возвращает содержательные картинки WebP, которые текущие
  PNG/JPEG/GIF-кодеки отвергают. Есть два реальных пропуска и два лишних
  placeholder от скрытых SVG. `images_omitted` и явные причины остаются;
  это частичный архив, допустимый по Q03, а не полный архив media.
- У Cloudflare Rust-код может быть ошибочно подписан CSS. Байты кода,
  пробелы и переносы сохранены; длинные строки прокручиваются горизонтально.
- Консервативный `text_incomplete` сохранён у всех источников. Навигация,
  формы/feedback и скрытые copyright/package-префиксы playground не выданы
  за основной материал; предупреждения не отключались ради скорости.

## Регрессия и воспроизведение

Успешно, отдельно от live benchmark: Go unit всех четырёх модулей, go vet,
`make test` (реальная PostgreSQL, worker 95,188 с), новые тесты safehttp/worker
под race detector, четыре теста метрик benchmark. Статусы и пути локальных журналов сохранены в
[checks.json](issue-22/checks.json). Проверены свежий DNS при reuse,
private/mixed DNS, смена IP/origin/port, blocked redirect, TLS verification,
отмена запроса, закрытие сессии между статьями, бюджеты повторных и
повреждённых изображений; существующие integration проверяют удаление,
deadline, stale publication и максимальный атомарный архив.

Первый полный `npm run test:e2e:integration` дал **99 passed, 4 failed / 103**.
История не удалена: [первый результат](issue-22/e2e-results.json), журнал
`tmp/issue-22-e2e-live.log`. Четыре ошибки были диагностированы:

- `delete during html` ожидал 404 от `page.request`, но получал 401: Playwright
  APIRequestContext не отправлял Secure-cookie на HTTP loopback. Браузерный
  запрос перед ним отправлял cookie и корректно получал 404.
- Та же проверка через APIRequestContext давала 401 вместо 200 после outage.
  Исправлены только тестовые запросы: они исполняются через fetch внутри
  авторизованного браузера с теми же ожидаемыми 404/200. Cookie остаётся
  Secure/HttpOnly, никакого переноса токена в JavaScript или ослабления API нет.
- После первого упавшего assertion тест не отпускал HTML drain barrier.
  Следующий media-сценарий не успевал достичь своей точки синхронизации.
  После перезапуска worker его media-запрос занял ещё 8 с до HTTP timeout;
  COMMIT-задача была взята только через 8,055 с, после своего 5-секундного poll.
  Это каскад оставленного состояния fixture. `afterEach` теперь освобождает
  незавершённые barriers; release-all идемпотентен и сохраняет ключи для поздних
  запросов. Fence, таймеры и assertions отмены/публикации не менялись.

Первое падение воспроизведено на чистом baseline commit
`6324743b2c01e8a79a8d870a184f531fd7c52c2a` в отдельном checkout под tmp,
без реализации reuse. Новая изолированная схема тестовой БД удалена harness;
рабочие данные не затронуты. Trace подтверждает отсутствие cookie только
у APIRequestContext и открытый незавершённый barrier. Значения cookies и
сырой trace не скопированы в документацию. [Диагноз и события каскада](issue-22/e2e-diagnosis.json).

Повтор полного E2E отдельно от benchmark: **103 passed / 103, 0 failed**,
включая все четыре ранее падавших и все реальные recovery-таймеры.
[Полный повтор](issue-22/e2e-fixed-results.json), журнал `tmp/issue-22-e2e-fixed.log`.
Сценарии login/library/reader проверены на 375×812, 768×1024 и 1440×900;
в `tmp/playwright/videos/integration/` проверено 117 непустых видео.
Новая регрессия очистки добавлена после сбора списка полного прогона и затем
выполнена отдельно: **1/1 passed** — [результат](issue-22/e2e-cleanup-result.json).
Таким образом, покрыты все 104 актуальных сценария без скрытого исключения тестов.
Это API-only проверка fixture без страницы браузера, поэтому видео для неё не создаётся.
Дополнительная проверка release-all использует настоящие зависшие HTML/media
HTTP-запросы, проверяет их завершение и повторные запросы по освобождённым ключам.
Новых live-серий и повторов уже зелёных Go unit/integration/race не выполнялось.

Ранее выполненный отдельный `make build` после первого E2E прошёл, включая Go
и production Next. Повторный E2E также собирает production Next; продуктовый
Go/UI-код в исправлении harness не менялся. Проверено совпадение всех backend
hashes с manifest финальной live-серии и hash benchmark driver. Результаты
50/60 и 57/60 остаются измерениями того же pipeline; серии не повторялись.
ESLint и TypeScript после изменения теста прошли.
Генерируемое изменение `web/next-env.d.ts` возвращено к исходному состоянию.
Сводный статус: [checks.json](issue-22/checks.json).
