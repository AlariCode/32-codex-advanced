# Резервная копия и восстановление личного архива

Архив — это не один JSON документа. Нужны `users` (включая Argon2id-хеши),
`user_sessions`, `links`, `processing_jobs`, `snapshots`, `assets` с бинарными
изображениями, все ключи, индексы, функции, триггеры и `schema_migrations`.
Таблицы связаны; выборочное копирование строк статьи не является этой процедурой.
Media сейчас целиком находятся в PostgreSQL: отдельный каталог файлов не нужен.
Полная копия содержит приватные данные всех пользователей выбранного окружения.

## Автоматическая проверка (только тестовая PostgreSQL)

Из корня репозитория, при установленных зависимостях (`npm ci` и
`npm ci --prefix web`), Go 1.26+, Node.js 22+, Docker Compose v2 и Chromium
Playwright (`cd web && npx playwright install chromium`):

```sh
make test-db-up
npm run test:archive:restore
```

Это отдельная команда, она включает браузерную часть. Обычная
`npm run test:e2e:integration` продолжает запускать существующий harness;
новый разрушающий исходную тестовую схему сценарий запускается отдельно.
Не запускать обе команды одновременно: они используют порты 3200, 18080,
39876, 39877 и production-сборку `web/.next`.

Harness не читает рабочий `DATABASE_URL` для подключения: он устанавливает свой
URL API/worker из `TEST_DATABASE_URL`. В режиме backup допускается только
`postgres://linkbook_test:linkbook_test_local@127.0.0.1:15433/linkbook_test?sslmode=disable`
(либо отсутствие переменной с этим значением по умолчанию). Проверка точного URL
происходит до создания данных. Dump/restore/createdb/dropdb выполняются только
через `docker compose -f compose.test.yaml exec -T postgres-test`, а не через
рабочий контейнер. Не перенаправлять этот сервис или порт на рабочую БД.
Тест не использует рабочие учётные записи и не экспортирует роли кластера.

Порядок проверки:

1. Создать уникальную схему `e2e_<pid>_<time>` в отдельной `linkbook_test`;
   API применяет настоящие миграции. Через API зарегистрировать двух владельцев,
   войти формой, сохранить собственную fixture-статью с PNG/JPEG/GIF и дождаться
   готового документа, опубликованного worker. Снять документ и SHA-256 media.
2. Остановить worker и API, закрыть HTTP-сервер оригинала. Готовый архив уже
   committed; остановка всех писателей исключает изменения между снимком и
   проверкой. Выполнить `pg_dump --format=custom --schema <schema> --no-owner
--no-acl` всей изолированной схемы в `tmp/backup-restore/<schema>/archive.dump`.
   Это настоящий согласованный PostgreSQL snapshot, не JSON-экспорт.
3. Создать новую БД `archive_restore_<pid>_<time>` из `template0` в том же
   тестовом контейнере. Выполнить `pg_restore --exit-on-error --single-transaction
--no-owner --no-acl`. Схема сохраняет своё имя, зависимости и migration checksums.
   Затем удалить исходную схему и запустить API с URL новой БД и её `search_path`.
   Worker восстановления не запускается, повторная загрузка оригинала не нужна.
4. Проверить недоступность socket оригинала. Очистить cookies браузера, войти
   штатной формой с прежним паролем. Сравнить публичный ID владельца и весь API
   документ до/после, прочитать настоящий renderer на 375×812, 768×1024 и
   1440×900: текст, strong/emphasis, цитата, список, code, подписи и три изображения.
   Проверить декодирование изображений, неизменные media URL, SHA-256 байтов,
   `no-store`, отсутствие запросов к оригиналу и горизонтального переполнения.
5. Войти вторым восстановленным пользователем: список не содержит архив,
   metadata/document/каждое media возвращают 404, renderer не показывает статью.
   Без сессии приватные API возвращают 401, reader отправляет на вход.

Видео успешного прогона, снимки трёх разрешений и `checksums.json` находятся
в `tmp/playwright/videos/backup-restore/`. Dump имеет права 0600, каталог 0700.
Приватные API-проверки тест выполняет через same-origin `fetch` в браузере:
Chromium отправляет Secure-cookie на HTTP loopback, а Playwright
`APIRequestContext` её там не отправляет. Проверки статусов 200/401/404,
заголовков и исходных байтов media сохраняются; атрибуты cookie не ослабляются.
Весь `tmp/` исключён из Git. Dump, traces и видео содержат приватные данные;
хранить их только в доверенном окружении и удалить после проверки.

## Согласованность и совместимость

Для переносимой копии реального окружения сначала закрыть входящие записи,
остановить worker и API, дождаться завершения транзакций/остановки процессов,
затем делать полный `pg_dump` базы (без `--schema`, если приложение использует
несколько схем). Нельзя копировать отдельно таблицы в разное время или файлы
живого PGDATA обычным файловым копированием. Сам `pg_dump` обеспечивает один
MVCC snapshot; остановка писателей задаёт понятную точку восстановления.
В тесте процессы убиваются только после публикации готовой статьи; PostgreSQL
откатывает незавершённые транзакции перед снимком. Незавершённая обработка не
проверяется этим сценарием.

Поддерживаемая проверенная конфигурация процедуры — PostgreSQL 18 и клиентские
`pg_dump`/`pg_restore` из того же образа `postgres:18-trixie` с тем же кодом
приложения и миграциями 001–006. Записывать git revision, версию PostgreSQL,
образ контейнера и настройки схемы рядом с операционной копией. Для долгого
хранения закрепить digest образа. Перенос на другую major-версию, другой набор
расширений или более старую версию приложения требует отдельной проверки.
Не редактировать migration history/checksums и не запускать старый API против
новой схемы. API автоматически проверяет/применяет миграции при старте; безопаснее
сначала восстановить с той же версией и проверить чтение, потом обновлять отдельно.

Восстанавливать только в пустую БД. Создать роли и необходимые расширения
отдельно: `--no-owner --no-acl` намеренно не переносит роли/права кластера.
В текущей схеме архива расширения не нужны; pgvector рабочего окружения и его
настройки не доказываются этой проверкой. Для полного окружения расширения
и их совместимые версии должны быть подготовлены заранее.

Настройки процессов не входят в dump: нужны корректные `DATABASE_URL` и
`search_path`, `API_ORIGIN` для Next (в том числе при сборке), `PUBLIC_ORIGIN`,
TLS/доверенный proxy для Secure cookie и конфигурация worker перед его запуском.
В тесте используются только loopback-адреса harness. Пароли пользователей
восстанавливаются как хеши; вход создаёт новую сессию. Сохранённые сессии могут
истечь к моменту восстановления, поэтому рассчитывать на старую cookie нельзя.
Секреты окружения и TLS-ключи хранить отдельно защищённым способом.

Это логический backup на момент снимка: последующие изменения теряются.
Нет PITR/WAL-архивации, переноса внешних media, восстановления удалённой до снимка
статьи, проверки незавершённых jobs, RPO/RTO или аварии целого кластера.
Тестовый источник и цель изолированы на уровне схемы/БД, но используют один
тестовый сервер PostgreSQL; проверка не моделирует потерю его диска.

## Cleanup

При успехе, ошибке, SIGINT или SIGTERM harness останавливает свои процессы,
удаляет исходную схему и новую БД (`dropdb --force --if-exists`). Dump и видео
сохраняются для проверки. При SIGKILL/потере питания автоматический cleanup
невозможен. Для полностью одноразовой тестовой PostgreSQL можно после остановки
всех тестов выполнить:

```sh
make test-db-down
```

У `compose.test.yaml` PostgreSQL хранится в tmpfs, поэтому это удаляет также
остатки прерванных тестов. Рабочий `compose.yaml` не затрагивается. Для повторного
запуска снова выполнить `make test-db-up`. После изучения артефактов удалить
нужные каталоги `tmp/backup-restore/` и `tmp/playwright/videos/backup-restore/`.
Не выполнять cleanup через рабочий `DATABASE_URL`.
