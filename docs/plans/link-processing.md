# План реализации: сохранение ссылок и чтение статей

Дата: 2026-10-13. Каркас и архитектурные варианты утверждены пользователем в текущем разговоре. Реализация не начата. Все перечисленные ниже проверки предназначены для будущей реализации и пока не выполнены.

## Цель

Вошедший пользователь сохраняет ссылку в личной библиотеке, автоматически получает результат фоновой обработки и читает сохранённую статью с базовым форматированием и изображениями. Архив остаётся доступным после изменения или исчезновения оригинала. Пользователь может повторить неудачную обработку и удалить любую свою карточку.

Основания:

- [PRD](../prd/link-processing.md).
- [Принятые продуктовые решения Q01–Q07 и лимиты](../research/link-processing/product-decisions.md).
- [Техническое исследование Q08–Q13](../research/link-processing/README.md).
- [Проверка библиотек](../research/link-processing/libraries.md) и [эксперименты с корпусом](../research/link-processing/experiments.md).

В разговоре согласован приоритет принятых Decisions над устаревшими открытыми вопросами и неполными таблицами PRD. В частности, результат без читалки имеет действие «Повторить». Decisions и PRD этим планом не редактируются.

Утверждённые варианты: 8A — Readeck в Go-worker; 9A + 9S — PostgreSQL для архива и ограниченная структура документа с React-renderer; 10A — защищённый HTTP-клиент и ограничения исходящего сетевого доступа; 11A — собственная PostgreSQL-очередь без River; 11P — polling; 12A — отдельный архив каждого пользователя; 13A — существующий ключ дедупликации отдельно от адресов загрузки и перенаправления. Исследовательские документы сохраняют исторический статус этих вариантов; основание их использования в плане — последующее утверждение каркаса.

## Архитектура

### Сквозной путь

1. Браузер показывает предварительную карточку и отправляет URL через same-origin Next.js proxy.
2. Go API проверяет сессию и входные данные, получает владельца из сессии и рассчитывает существующий ключ нормализации.
3. API одной транзакцией создаёт карточку и задачу. При совпадении возвращает существующую карточку владельца.
4. Worker забирает задачу из PostgreSQL с ограниченной арендой исполнения, безопасно загружает страницу и извлекает содержимое Readeck. Внешние запросы и парсинг выполняются вне долгой SQL-транзакции.
5. Worker преобразует результат в разрешённую структуру, загружает и проверяет изображения. Одной транзакцией публикует документ, изображения и итоговое состояние, проверяя актуальность исполнения и deadline.
6. Браузер опрашивает активные карточки одним пакетным запросом каждые две секунды и обновляет список. Читалка получает документ и приватные изображения из API.

### Надёжность очереди

- Запись карточки/ручного повтора и enqueue атомарны. PostgreSQL — источник истины; закрытие браузера не влияет на сохранённую задачу.
- Получение задачи — короткая транзакция с блокировкой, пропускающей уже захваченные строки. Сетевой запрос не удерживает эту блокировку.
- Аренда исполнения ограничена по времени и продлевается только актуальным исполнителем. После её истечения задача может быть захвачена повторно в пределах исходного общего deadline.
- Ручная попытка имеет generation, каждое исполнение этой попытки — новый execution_token. Проверка обоих значений исключает публикацию зависшего старого исполнения после восстановления аренды.
- Deadline хранится в БД и не сдвигается из-за аренды, рестарта или внутренних retries. Бюджет — 120 секунд от серверной фиксации сохранения или ручного повтора, включая очередь.
- API обслуживает истёкшие попытки независимо от worker; чтение также не возвращает просроченную попытку как продолжающую обработку. При полной недоступности системы отображение результата в браузере ровно в срок не обещается.
- Публикация проверяет существование карточки, текущую generation, execution_token, допустимое состояние и непросроченный deadline. Snapshot, assets, состояние карточки и завершение задачи фиксируются согласованно.
- Ограниченные внутренние retries допустимы для временных сетевых сбоев, 429 и 5xx с учётом Retry-After и оставшегося бюджета. Отсутствие статьи не вызывает бесконечных retries.
- Доставка задач допускает повторное исполнение. Требуется безопасная повторяемость результата, а не обещание единственного запуска.

### Загрузка, документ и доступ

Для HTML и каждого изображения применяется одна сетевая политика: HTTP(S), запрет userinfo и неоднозначных адресов, проверка DNS и каждого redirect, блокировка непубличных/служебных адресов, привязка соединения к проверенному IP с корректными Host/TLS, отсутствие пользовательских cookies и автоматического proxy из окружения. Предусмотреть также запрет доступа во внутренние сети на уровне среды запуска worker. Нормализация URL не считается SSRF-защитой.

Submitted URL предназначен для отображения, fetch URL сохраняет исходную схему и значимые параметры загрузки без fragment, dedup key соответствует существующему NormalizeURL, final URL служит метаданными. Redirect/canonical не объединяют карточки автоматически. Дополнительные ограничения URL, меняющие пользовательскую семантику, не выводятся молча из исследовательских предложений.

Readeck получает уже загруженный HTML, не выполняет самостоятельную неконтролируемую загрузку и не исполняет JavaScript страницы. PDF, видео, главные страницы и формы входа/оплаты классифицируются отдельно. Успешная загрузка без убедительно извлечённой статьи даёт unavailable; сеть, системный сбой и deadline — failed. Один размер текста или отсутствие ошибки парсера не доказывают наличие статьи.

Документ содержит только разрешённые текстовые блоки, заголовки, списки, цитаты, inline emphasis, ссылки, pre/code, изображения и подписи. Таблицы и details сохраняются через явно описанные элементы схемы, когда встречаются в корпусе. Renderer создаёт известные React-элементы; сырой HTML, произвольные props/styles, SVG, MathML, iframe, forms и обработчики событий из оригинала не выдаются. Ссылки проходят проверку HTTP(S); открытие отдельной вкладкой получает безопасный rel.

Изображения определяются в основном содержимом с учётом относительных адресов, final URL, проверенного base, srcset и lazy-loading атрибутов. Для каждой позиции выбирается один доступный вариант. Проверяются байтовая сигнатура, декодирование, размеры, число пикселей и, для анимации, кадров/памяти. Поддерживаемые кодеки и технические пределы декодирования фиксируются при реализации по корпусу и бюджету ресурсов; непроверенный формат не выдаётся как безопасный. Пропущенные изображения имеют предупреждение и placeholder, без клиентского fallback на внешний URL.

Личные ответы получают Cache-Control: no-store. Media выдаётся с проверенным MIME и nosniff после проверки владельца. CSP читалки ограничивает изображения своим origin и не разрешает активное содержимое статьи, сохраняя совместимость с Next.js. Изменяющие состояние запросы проверяют Origin/CSRF с учётом доверенного same-origin proxy.

Серверные состояния карточки: processing, ready, unavailable, failed. Черновик, отправка и неизвестный исход запроса — отдельные клиентские состояния. После 30 секунд processing остаётся processing; меняется только сообщение. Предупреждение не заменяет итоговое состояние.

Инварианты:

- Владелец всегда определяется сервером из сессии, не из тела запроса.
- Уникальность дедупликации обеспечивается БД, включая конкурентные добавления. Нельзя полагаться на предварительный SELECT.
- Ключ URL может превышать практический размер индексной записи PostgreSQL: реализация должна учитывать это. При использовании digest для индекса совпадение обязательно сверяется с полным ключом; коллизия не должна возвращать чужую по URL карточку.
- Индекс списка поддерживает фильтр владельца и стабильный порядок. Предусмотреть ограниченную keyset-пагинацию; polling охватывает активные карточки независимо от текущей страницы.
- Нет общей дедупликации контента между владельцами. Удаление одного архива не затрагивает другого.
- Текст и изображения публикуются вместе. Непрошедшие проверку и устаревшие промежуточные результаты не становятся доступными через API.
- HTML ограничен 3 MiB после декомпрессии; один сохранённый image — 5 MiB, все изображения статьи — 20 MiB, число изображений — 50. Потери из-за лимитов обозначаются предупреждениями.
- Ограниченный фрагмент HTML нельзя объявлять полным документом. Если из него получен пригодный частичный текст, публикация требует предупреждения; если статьи нет, действует unavailable; технический сбой сохраняет свою классификацию.
- Запасной заголовок: извлечённый заголовок, затем метаданные страницы, затем hostname. В processing основным содержимым карточки остаётся URL.

Существующие users и user_sessions не требуют заполнения или пересоздания. Начальная библиотека пуста. Миграции добавляются после 002, ранее применённые файлы и их checksum не меняются. Проверить upgrade существующей БД, чистую установку и повторный запуск. JSON-схема документа версионируется; несовместимый документ вызывает контролируемую ошибку, а не небезопасный fallback на HTML.

| GET /api/links/{id}/assets/{asset_id} | Cookie, ID карточки и asset        | Проверенные сохранённые байты собственного asset с MIME, nosniff и no-store; без внешнего перенаправления                                                             | 2                       |
| POST /api/links/{id}/retry            | Cookie и ID                        | Новая generation и задача для failed/unavailable с новым 120-секундным бюджетом; повторный запрос к processing возвращает текущую попытку без дополнительного enqueue | 2                       |
| DELETE /api/links/{id}                | Cookie и ID после подтверждения UI | 204 после удаления карточки, документа, assets и задач; чужой/отсутствующий ID — одинаковый 404                                                                       | 4                       |

Карточка DTO содержит ID, отображаемый URL, заголовок при наличии, состояние, generation, reason/warnings, даты создания и начала попытки, deadline и признак доступности читалки. API предоставляет серверное время для корректного отображения ожидания при несовпадении часов браузера. Внутренние execution_token, сетевые адреса, stack traces и содержимое сессии клиенту не передаются.

Общие ошибки:

- 400 — некорректный URL, ID или параметры; ошибка URL позволяет исправить предварительную карточку.
- 401 — требуется вход; личное содержимое немедленно скрывается и повторно проверяется после входа.
- 403 — отказ Origin/CSRF, без изменения данных.
- 404 — одинаковый ответ для чужой и отсутствующей карточки/картинки.
- 409 — несовместимое состояние операции, например чтение документа до ready; клиент сверяет карточку.
- 413/415 — превышение допустимого тела API/неподдерживаемый Content-Type по существующему транспортному подходу.
- 5xx или сетевой сбой отправки не доказывают отсутствие commit. Черновик остаётся; повтор POST возвращает единственную карточку по нормализованному URL.

Ошибки фоновой обработки — данные карточки, а не ошибка HTTP-загрузки списка: понятные коды сетевого сбоя, запрета назначения, deadline или внутренней обработки. У unavailable — причина отсутствия статьи. Не отображать внутренние IP и секретные query-параметры в диагностике.

Повтор HTTP-загрузки списка/документа отличается от повторной обработки: первый повторяет GET и сохраняет существующий архив, второй создаёт новую попытку только через retry. Дубликат POST добавления не запускает обработку заново и не меняет created_at.

Polling активен каждые две секунды только при наличии processing. В скрытой вкладке частый polling приостанавливается; при focus, восстановлении сети и возвращении на страницу выполняется немедленная сверка. Терминальные карточки исключаются из частого опроса. Переходы состояния одной карточки учитывают generation, чтобы поздний HTTP-ответ не заменил новую попытку.

После входа разрешены только безопасные локальные returnTo. Обычный вход без returnTo сохраняет существующий путь на главную; возврат к читалке заново проверяет владельца и существование статьи. Приватные данные другого аккаунта не берутся из старого React/Next/browser cache.

Контракты документируются в backend/api и аннотациях Swagger. Генерация — существующей командой make openapi. Новые rewrites перечисляются явно; API_ORIGIN не задаётся пользовательским URL.

Нужна новая команда npm run test:e2e:integration, которой сейчас нет. В фазе 1 добавить её вместе с отдельной Playwright-конфигурацией и воспроизводимым запуском Next.js, API, worker и изолированной схемы linkbook_test. Для настоящего сценария обработки нужен контролируемый HTTP fixture-server и оригинальные fixtures проекта. Его доступность в тестовой сети обеспечить узкой политикой, существующей только в тестовом harness; production-проверки публичных адресов не отключать. Отдельные проверки сетевой защиты используют production-policy. Успешный тест действительно проходит через очередь, загрузку, Readeck, сохранение и renderer, без подмены ключевых звеньев готовым результатом.

### Фаза 1. Сохранить и прочитать текстовую статью

**Результат.** Вошедший пользователь сохраняет обычную статическую статью без изображений; предварительная карточка появляется сразу, сервер сохраняет её и задачу, реальный worker извлекает текст, карточка автоматически получает заголовок, статья читается из PostgreSQL. В пустой библиотеке есть предложение сохранить первую ссылку. Закрытие страницы и рестарт worker не теряют задачу.

**Изменения.**

- Добавить новый общий Go-модуль и включить его в workspace, go vet, обычные и интеграционные тесты.
- Создать миграции links, processing_jobs и snapshots с owner-scoped дедупликацией, generation, execution_token, lease и durable deadline. Применять существующим мигратором API.
- Добавить проверку текущей сессии, владельца, no-store и Origin/CSRF; закрыть все новые приватные маршруты до подключения UI.
- Реализовать список, добавление, метаданные, статусы и документ. Сохранение link+job атомарно; конкурентный дубликат возвращает существующую запись.
- Подключить worker к БД; реализовать claim, lease renewal/reclaim, ограниченные transient retries, deadline и безопасную публикацию. Обслуживание истёкших попыток работает и при остановленном worker.
- Добавить защищённую загрузку HTML, лимит декомпрессии, реальные Readeck extraction и преобразование базовой структуры. Ключ нормализации не использовать как адрес загрузки.
- Добавить библиотеку и текстовую читалку в _pages, routes и rewrites. Предварительная карточка различает валидацию, отправку, processing и ошибку сохранения; исправление и повтор HTTP-отправки доступны сразу.
- Через 30 секунд показывать «Обработка занимает больше времени», через 120 — failed; отсчёт не начинается заново после reload. При успехе включается переход в читалку с возвратом в список и открытием оригинала.
- Добавить сквозной тестовый harness и fixtures; сохранить регрессионные проверки входа/регистрации. При потере авторизации уже в этой фазе скрывать личные данные, даже до полного возврата из фазы 3.

**Зависимости.** Доступная PostgreSQL тестового/рабочего окружения, существующие пользователи и сессии, разрешённый доступ worker к публичным сайтам и настроенная сетевая изоляция. Readeck и транзитивные версии закрепляются в Go manifests; исследовательские прототипы не копируются как готовая production-реализация.

**Проверка.** Команды из корня: make check, make test, npm run test:e2e, новая npm run test:e2e:integration, make build, make openapi. Новая команда должна быть реализована в этой фазе, а не подразумеваться существующей.

Ручные/браузерные сценарии и ожидаемые результаты:

1. Войти, открыть пустую библиотеку, сохранить собственную text-only fixture-статью: предварительная карточка видна до ответа POST, затем processing, автоматически ready; читалка содержит ожидаемые абзацы, заголовки, список и цитату без menu/footer.
2. Отключить оригинал после ready, обновить читалку: сохранённый текст доступен.
3. Отправить некорректный адрес и затем исправить его: ошибка находится в карточке, исправление приводит к реальной обработке. Ошибка самого POST позволяет повторить отправку.
4. Добавить одинаковые после нормализации URL последовательно и конкурентно: одна строка links, одна начальная задача, сообщение «Ссылка уже сохранена» и переход к существующей карточке. Разные владельцы получают независимые карточки.
5. Замедлить fixture-загрузку: после 30 секунд меняется сообщение, обработка продолжается; после 120 секунд общего ожидания — failed. Отдельно держать задачу в очереди при остановленном worker: API фиксирует timeout; последующий запуск не публикует просроченный результат.
6. Закрыть страницу после подтверждения POST, открыть снова: актуальное состояние получено из БД. Остановить worker после claim и запустить снова: задача восстанавливается по lease; старый execution_token не может опубликовать результат.
7. Без сессии и от другого владельца запросить список, карточку и документ: 401 либо одинаковый 404 для чужого/отсутствующего ID; чужое содержимое отсутствует. Cross-origin запись отклоняется.
8. Проверить блокировку private/loopback/metadata, IPv4-mapped IPv6, redirect на закрытый адрес, смену DNS и превышение распакованного HTML. Проверить, что HTTP-only fixture не превращается в HTTPS-загрузку из-за dedup key.

Критерий завершения: text-only путь работает на реальных API, БД и worker; миграции применяются к существующей БД; проверки и визуальный/UX-проход зелёные. Никакой заглушки вместо очереди, загрузки, извлечения или хранения.

**На потом.** Изображения, полная схема, классификация отсутствия статьи и ручной retry — фаза 2; долговременный локальный черновик, полный возврат после входа и восстановление ошибок чтения — фаза 3; удаление и его гонки — фаза 4. Эта фаза проверяется на text-only сценарии и не заявляет выполнение требований архива изображений.

### Фаза 2. Читать полный доступный архив

**Результат.** Статья сохраняется с форматированием и проверенными изображениями и читается после отключения оригинала. Частичные результаты показывают предупреждения. Страницы без доступной статьи остаются ссылками; failed и unavailable допускают новую попытку в той же карточке.

**Изменения.**

- Добавить assets и связи с опубликованным документом, приватный media route и поддержку image/figure/caption в renderer. Дополнить схему необходимыми элементами корпуса, включая pre/code и таблицы.
- Разобрать relative/srcset/lazy image candidates и безопасный base; все загрузки и redirects проходят ту же политику, что HTML.
- Проверять форматы, декодирование и ресурсные пределы; соблюдать 5 MiB на изображение, 20 MiB суммарно, 50 изображений. Пропуски, неполный текст и достижение HTML-лимита сопровождаются понятными предупреждениями.
- Проверить набор кодеков на реальных изображениях корпуса. Неподдерживаемые изображения не загружаются браузером с оригинала; невозможность их сохранить явно отражается в результате.
- Публиковать документ, assets, состояние и завершение задачи одной согласованной транзакцией с fence. Читалка не видит наполовину опубликованный архив.
- Добавить классификацию главной страницы, PDF, видео, login/paywall и JS-only оболочки. Отсутствие извлечённой статьи после загрузки — unavailable, а не системная ошибка. Не обходить ограничения оригинала.
- Добавить запасной заголовок: извлечение → metadata → hostname; причины unavailable и предупреждения ready.
- Реализовать retry для failed/unavailable: новая generation и новый deadline, одна активная попытка. Карточка возвращается в processing и автоматически обновляется. Ошибка HTTP-запроса retry не создаёт параллельные задачи.
- Добавить открытие оригинала в итоговых карточках, предупреждения/placeholder в читалке, CSP и проверку отсутствия внешних подресурсов статьи.
- Добавить воспроизводимую методику измерения скорости и отдельный явный запуск benchmark по живому корпусу; не включать нестабильный интернет-бенчмарк в обычные детерминированные тесты.

**Зависимости.** Работающая фаза 1, ограниченный сетевой доступ для media, выбранные и проверенные image decoders. Корпус и ограничения исследований используются как исходные данные, не как доказательство качества готовой фичи.

**Проверка.** Make check, make test, npm run test:e2e, npm run test:e2e:integration, make build, make openapi. Добавить новую явно документированную команду benchmark; до её появления готового скрипта измерения в проекте нет.

Сценарии:

1. Сохранить fixture с форматированием, relative/lazy/srcset изображениями и подписями. После ready остановить HTTP fixture-server, открыть читалку заново: текст и изображения доступны через приватный API, внешние image requests отсутствуют.
2. Отдельно превысить HTML, размер одного изображения, суммарные bytes и число изображений; вернуть битое/неподдерживаемое изображение. Ресурсные лимиты соблюдены, доступный частичный результат имеет предупреждение и места пропусков. Нет молчаливой обрезки.
3. Сохранить главную, PDF, видео, форму входа/оплаты и JS-only fixture: unavailable с пояснением, без фиктивной читалки; заголовок при возможности, оригинал и повтор доступны. Сетевая ошибка отдельно даёт failed.
4. Повторить failed/unavailable после изменения fixture на доступную статью: тот же ID и created_at, новая generation, processing → ready. Конкурентные retry не создают две активные задачи; старый результат и старый polling-ответ не заменяют новый.
5. Передать XSS/активные URL/внешний tracker в оригинале: небезопасные узлы не исполняются, активные атрибуты не передаются, изображения выдаются только из архива. Чужой asset недоступен даже при известном ID.
6. Пройти весь RU/EN-корпус и методику скорости ниже. Качество и время фиксируются отдельно; быстрый непригодный результат не считается успехом.

Методика приёмки качества: для шести статей go-strings, go-pipelines, MDN Introduction, Cloudflare Pingora, Habr GC и Habr Avito из [корпуса](../research/link-processing/experiments.md#q08-извлечение) вручную сверить весь основной текст, смысловые заголовки, списки, цитаты, код, таблицы, изображения и подписи, если они присутствуют. Меню/реклама/формы входа не становятся текстом статьи. Выявленные потери сопровождаются предупреждениями; отсутствие предупреждения не трактуется как доказательство универсальной полноты. Сохранить отчёт с конкретными расхождениями, не только счётчиками DOM.

Согласованная методика скорости: десять новых сохранений каждой из шести статей, всего 60; минимум 54 готовых результата отображаются в карточке не позднее 15 секунд от серверного подтверждённого сохранения. Измерение включает очередь, загрузку HTML/media, обработку, commit и задержку polling. Готовность означает опубликованный пригодный документ с результатом архивирования изображений; дубликат, unavailable и failed не засчитываются как успешная обработка обычной статьи. Для новых сохранений использовать независимые тестовые аккаунты, не обходить дедупликацию изменением исходных страниц. Выполнять последовательные сохранения на зафиксированном окружении, записать версии, настройки concurrency, ресурсы и сетевые условия. Исходные условия и все неудачные прогоны входят в отчёт; менять состав корпуса после просмотра результатов нельзя. Проверки нескольких одновременных задач выполняются отдельно и не подменяют эти 60 измерений.

Критерий завершения: независимый архив текста/media, классификация, предупреждения и retry работают сквозным путём; корпус проверен, скорость измерена. При невыполнении порога 54/60 устранить причину или зафиксировать невыполненный критерий; не объявлять цель достигнутой по времени одного парсинга.

**На потом.** Локальное восстановление неизвестной отправки и полноценный возврат после входа — фаза 3; удаление и дополнительные гонки жизненного цикла — фаза 4. Browser fallback, обход paywall, общий контент и S3 — вне текущего объёма.

### Фаза 3. Продолжить после сбоя или повторного входа

**Результат.** Пользователь возвращается к своему черновику после закрытия страницы, разрешает неизвестный исход отправки без серверного дубликата, исправляет URL и переходит к уже сохранённой карточке. Ошибки списка/читалки допускают повтор, истечение сессии ведёт ко входу с возвратом и новой проверкой доступа.

**Изменения.**

- Сохранять локальный черновик с user_id только для проверенного аккаунта, различая ещё не отправленный адрес, отправку, ошибку и неизвестный исход. Подтверждённую серверную карточку не считать черновиком.
- После reload показывать черновики только после проверки текущей сессии; при неизвестном исходе предлагать повторить отправку. POST с тем же URL либо создаёт отсутствующую запись, либо возвращает существующую. После подтверждения слить предварительную карточку с серверной и удалить локальный черновик.
- При исправлении URL на уже сохранённый показать «Ссылка уже сохранена» и открыть существующую карточку; не менять чужую предварительную карточку и не создавать новую задачу существующей.
- В shared/auth сосредоточить общий сброс публичной сессии и приватных UI/cache при 401 и смене аккаунта. Не хранить cookie token в localStorage.
- Добавить безопасный returnTo в login flow; после входа снова проверить session, владельца и существование карточки. Отсутствующая статья даёт понятный переход в библиотеку, внешний returnTo не используется.
- Добавить состояния первой ошибки загрузки списка/документа с «Повторить». При последующих сетевых сбоях сохранять уже загруженный контент и показывать ошибку обновления. При 401 личное содержимое скрывать, а не сохранять на экране.
- После offline/focus/history restore сверять сессию и данные; игнорировать поздние запросы предыдущего аккаунта/попытки. Не показывать черновики или сохранённый документ другого пользователя.

**Зависимости.** Фазы 1–2, серверная дедупликация, проверка session и owner на каждом приватном маршруте. Блокировка localStorage браузером не должна ломать сохранение: сообщить о недоступности восстановления черновика и продолжить работу в памяти.

**Проверка.** Make check, make test, npm run test:e2e, npm run test:e2e:integration, make build. Обновить реальные интеграционные сценарии и отдельные UI-тесты сетевых сбоев; API mock допустим для управляемой UX-ошибки, но основной путь восстановления дополнительно проверяется с настоящим API.

Сценарии:

1. Ввести адрес, закрыть страницу до отправки, вернуться тем же аккаунтом: черновик восстановлен и ещё не выглядит сохранённым. Другой аккаунт этого черновика не видит.
2. Прервать получение ответа после успешного commit POST: черновик остаётся с неизвестным исходом. Повторить отправку, в том числе после reload: API возвращает единственную существующую карточку, UI сливает её с черновиком.
3. Исправить ошибочный адрес на вариант имеющейся ссылки: сообщение о дубликате и переход к ней, число карточек и задач не растёт.
4. Отключить API при первой загрузке списка и читалки: экран ошибки с повтором. Отключить после успешной загрузки: содержимое остаётся, повтор восстанавливает актуальные данные.
5. Истечь сессию во время добавления, polling и чтения: приватные данные скрыты, переход ко входу, затем возврат на прежний безопасный путь. Сохранённая задача продолжает выполняться независимо от сессии.
6. Во время повторного входа выбрать другой аккаунт, затем Back/history restore: старый документ и черновики не отображаются; сервер возвращает 404 для чужой статьи. Поздний ответ старого аккаунта не попадает в новый UI.
7. Передать внешний, protocol-relative и некорректный returnTo: внешнего перенаправления нет. Если статья исчезла за время входа, доступ корректно перепроверяется.

Критерий завершения: все ветки Q05/Q07 и возврат после входа из Q06 работают на трёх разрешениях; черновик никогда не выдаётся за подтверждённую запись, приватные данные не переносятся между аккаунтами.

**На потом.** Удаление, отмена исполнения и расширенная матрица retry/delete/restart — фаза 4. Синхронизация неотправленных черновиков между устройствами — вне текущего объёма.

### Фаза 4. Удалить карточку в любом состоянии

**Результат.** Пользователь подтверждает удаление любой своей карточки. Только подтверждённое сервером удаление убирает её из библиотеки; при ошибке карточка остаётся. Обработка отменяется, поздний worker или HTTP-ответ не восстанавливает удалённое содержимое. Остальные согласованные сценарии проходят итоговую приёмку вместе.

**Изменения.**

- Добавить DELETE и owner-scoped транзакционное удаление link, jobs, snapshot и assets. Проверка существования карточки остаётся обязательным условием публикации worker.
- Добавить подтверждение удаления без undo, состояния запроса/ошибки и повтор удаления. Не скрывать карточку оптимистически до результата сервера.
- При удалении processing останавливать локальное исполнение через отмену context/проверку существования задачи. Доставка отмены — best effort; корректность обеспечивается fence и отсутствием строки даже при продолжающемся внешнем запросе.
- Удалённый ID исключать из polling; поздние ответы не вставляют его обратно. При неизвестном исходе DELETE повторно сверить сервер; 404 для известной карточки требует подтверждения её отсутствия, а не восстановления из локального cache.
- Если удалена открытая статья, закрыть её приватное содержимое и дать переход в библиотеку. Старые document/media URL больше не дают доступ к удалённому архиву.
- Расширить конкурентные и процессные сценарии add/retry/delete/lease reclaim, включая два worker и остановку исполнителя во время публикации. Базовые lease/deadline уже реализованы в фазе 1.
- Добавить необходимую наблюдаемость: возраст очереди, processing/deadline/failed/reclaimed, продолжительность этапов и сохранённые bytes; не логировать токены и чувствительные URL. Зафиксировать условия восстановления БД с media.

**Зависимости.** Фазы 1–3, атомарная публикация и каскадные связи. Возможность управляемо останавливать worker и внешний fixture-server в интеграционном окружении.

**Проверка.** Make check, make test, npm run test:e2e, npm run test:e2e:integration, make build, make openapi; итоговый явный запуск benchmark по методике фазы 2. Проверить, что команды включают общий Go-модуль и что все требуемые видео действительно созданы.

Сценарии:

1. Для processing, ready, unavailable и failed отменить подтверждение удаления: данных не меняется. Подтвердить: после 204 карточка исчезает, текст/media/задачи недоступны; восстановления нет.
2. Вернуть ошибку DELETE до commit: карточка остаётся с повтором. Потерять ответ после commit: сверка подтверждает отсутствие, повтор не создаёт карточку.
3. Удалить карточку после claim, во время загрузки изображения и непосредственно перед commit результата: ни одно исполнение не публикует документ или media удалённой карточки.
4. Одновременно выполнить retry и delete в разных вкладках, повторный claim в двух worker и позднюю публикацию старого execution_token: нет воскрешения, двух актуальных результатов или замены новой generation старой.
5. Удалить статью в другой вкладке и вернуться в открытую читалку: новая серверная проверка закрывает доступ; повтор загрузки media возвращает 404. Другой владелец не может удалить карточку.
6. Остановить worker во время исполнения, дождаться deadline и запустить снова: API показывает timeout, поздний результат не появляется. При полной остановке API/worker после восстановления корректно обрабатываются накопившиеся deadlines.
7. После удаления сохранить тот же URL заново: новая карточка и новая задача без конфликта с остатками старого архива.
8. На тестовой БД проверить backup/restore готовой статьи с изображениями при отключённом оригинале. Пройти всю таблицу критериев, корпус, три разрешения и регрессию входа/регистрации.

Критерий завершения: все обязательные требования PRD и согласованных Decisions покрыты реализованными фазами и проверками; 54/60 измерений укладываются в 15 секунд, качество проверено отдельно, архив восстанавливается без оригинала. Непройденный критерий остаётся явным препятствием завершению фичи, а не переносится в неопределённое «потом».

**На потом.** Обязательных требований текущего объёма не остаётся. Масштабирование на большой поток, SSE, browser extraction, межпользовательская дедупликация и объектное хранилище — вне текущего объёма.
